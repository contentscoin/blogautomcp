# MCP·데스크탑 블로그 포스팅 코드 종합 분석

작성: 2026-09-07. 분석 기준: HEAD `10634b6`, 작업 트리 및 설치 앱 1.3.25.

**여섯 증상을 설명하는 복수의 코드 결함을 확인했다. 핵심은 초안 평가의 기준 불일치, 기존 MCP 초안의 자동 수정 미지원, 이미지 슬롯 식별자 충돌, Electron 예약 입력 오류, 외부 발행 결과 판정과 MCP 완료 전송의 복구 누락이다.** 점수를 낮추거나 승인 검사를 없애는 것으로 해결할 문제가 아니다.

이번 산출물은 원인 분석과 재현 자료다. 운영 코드 수정·앱 업데이트·배포·실제 포스팅·유료 이미지 생성은 하지 않았다. 사용자가 지정한 대로 화면 분석은 수행하지 않았다. 프런트엔드 이벤트 핸들러는 API 도달 여부를 판단하기 위해 코드만 읽었다.

## 2. 시스템 경계와 상태 흐름

```text
MCP 사용자 요청
  → Sites 도구 스키마/권한/중복 요청 검증
  → 중앙 agent_jobs QUEUED
  → 데스크탑 poll: claim + heartbeat
  → 로컬 auto-publish / bulk API
      → 저장 초안 재사용 또는 작성
      → 이미지 보충
      → 재검사 → 승인 → 필요시 보강 1회 → 재검사 → 승인
      → Naver 에디터 제출 → 결과 확인 → 로컬 DB 기록
  → 완료 outbox → 중앙 complete → MCP job_get

데스크탑 예약 버튼
  → 날짜 입력(prompt에서 실패)
  → 이후는 같은 auto-publish 경로
```

상품의 예약은 앱 내부 cron에 넣었다가 나중에 실행하는 방식이 아니라 **지금 네이버 에디터에 들어가 미래 날짜의 예약을 등록하는 방식**이다. `src/services/scheduler.ts`의 주제글 scheduler만 고쳐서는 상품 예약 버튼이 해결되지 않는다.

현재 상태의 권위가 여러 군데로 나뉜다: 중앙 job, 메모리 Map, 상품 DB 상태, 초안 manifest의 승인/QC, 이미지 journal. 동일한 draft revision/attempt를 공유하지 않는 부분에서 오래된 상태·재시작 소실·완료 오판이 생긴다.

## 3. 증상 1과 6: 점수 자체보다 평가·보강 계약을 먼저 통일해야 한다

### 평가 결과의 불일치

`src/lib/brand-post-package.ts:431-435`는 `specValidation`을 먼저 readiness로 반환한다. 실제 승인 `:333-359`는 그 값 대신 구성/내용 검사를 확인한다. 이후 이미지 반영 `:558-571`에서 구성과 내용은 바뀌지만 specValidation은 남을 수 있다. 따라서 총점뿐 아니라 보강 대상 목록까지 서로 다른 평가 시점의 값이 될 수 있다.

`scripts/simple-agent.ts:9401-9441`의 수정은 현재 DB로 채점하고 이전 sourceSnapshot을 유지한다. `src/lib/brand-post-revalidation.ts:90-106`의 재검사는 그 snapshot으로 채점한다. **동일 원고의 점수가 바뀌는 원인이 글 변경이 아니라 채점 입력 변경일 수 있다.** 현재 저장 샘플에서 실제 DB/snapshot 차이가 일어났는지는 확인하지 않았다.

### 자동 보강의 형식 불일치

`scripts/lib/scheduled-draft-workflow.ts:63-72`는 CONTENT_BLOCKED면 무조건 revise를 호출한다. 하지만 `src/app/api/brandlinks/[id]/draft/route.ts:314-317`은 postSpec이 없는 초안을 거절한다. 검증된 출처가 있고 본문도 저장되어 있어도 MCP 제출 형식이면 자동 수정이 끝나지 않는다. 사람이 다시 승인한다고 수정 기능이 생기는 것은 아니다.

### 실제 저장 샘플의 판정

읽기 전용으로 확인한 여행 초안 1건은 content 80점, composition 56점, approvedAt 없음, sourceSnapshot 있음, postSpec 없음이었다. 내용 검사에는 장소 근거와 장면 연결 각각 2/3이라는 실패가 있었다. 80점은 이 감점 산식과 일치하며, **점수 계산이 틀려서만 승인이 안 난다고 결론 내릴 수 없다.** 장소 의미 매칭이 적절했는지는 문장별 출처/원문 비교가 추가로 필요하다.

수정 시 `snapshotId + textHash + imageSlotRevision + evaluatorVersion`에 연결된 공통 평가 결과를 만들고 미리보기·MCP·승인·보강이 함께 사용해야 한다. 총점, 필수 내용 통과, 이미지 통과, 해결할 섹션/근거를 별도 필드로 제공해야 한다. 높은 점수만 보고 승인시키는 우회는 하지 않는다.

## 4. 증상 2와 3: 입력 실패와 제출 이후 불확실성을 분리해야 한다

- 예약 버튼: `src/app/page.tsx:1419`의 native prompt를 날짜 입력 모달로 바꾸는 것이 직접 수정이다. 오류 메시지만 붙이면 예약은 여전히 안 된다.
- 클릭 결과: `scripts/simple-agent.ts:8925-8927,9031-9033,9045-9047`은 click 오류를 삼키고 성공을 반환한다. 클릭 실패, 요청 제출, 서버 성공을 별도로 관측해야 한다.
- URL 판정: `simple-agent.ts:9181-9182`와 `src/app/api/brandlinks/[id]/verify/route.ts:13-21`이 허용하는 글 주소가 다르다. 호스트·계정·글 번호를 확인하는 공용 parser가 필요하다.
- 결과 불확실: URL 미확인(`:10112-10114`)이나 이미 성공한 뒤 정리 오류가 전체 catch(`:10176`)에서 FAILED로 저장될 수 있다. FAILED는 다시 발행 가능한 상태다.
- 예약 검증: `src/lib/naver-schedule-submission.ts:35,52`는 요청 형태와 HTTP 코드만 확인한다. HTTP 200의 업무 오류 본문이나 등록 ID를 검증하지 않으므로 실제 예약 등록 성공과 같지 않다.

발행 attempt에 `제출 전 실패`, `제출 중`, `결과 확인 중`, `성공`, `결과 불확실`을 남겨야 한다. 제출 이후 연결 손실은 자동 재발행의 근거가 될 수 없다. 성공한 발행은 알림/브라우저 정리 오류로 실패로 덮어쓰지 않아야 한다.

## 5. 증상 5: 이미지 슬롯 충돌이 승인 실패로 이어진다

`src/lib/brand-post-image-generation.ts:238-246`의 재개 식별자에는 같은 섹션 안의 슬롯 번호가 없다. 부족한 2장을 요청하면 transport ID는 달라도 raw 경로와 checkpoint는 같다. worker `scripts/chatgpt-generate-image-batch.ts:342-344`는 둘째 작업에서 첫째 결과를 재사용한다. 여행은 raw 파일을 그대로 적용하고 package `:598-599`는 동일 SHA를 거절한다.

여행 계약 `src/lib/post-composition-contract.ts:287`은 실제로 최소 2장의 방문지 이미지를 요구한다. 따라서 **2장 필요 → 1장만 적용 → 다시 같은 이미지 → 중복 거절 → 이미지 부족 → 승인 보류**라는 반복이 발생할 수 있다. 단순 재시도 횟수 확대가 해결책이 아니다.

또한 모든 글이 같은 ChatGPT 프로필 잠금을 사용하고 한 배치가 끝날 때까지 점유한다. 다른 worker는 기본 10분 뒤 busy 실패할 수 있다. 현재 bulk 실행 자체는 순차지만, 별도 초안 작업/다른 진입점이 겹치면 이 충돌이 가능하다.

본문 이미지는 ChatGPT 브라우저 batch, 최초 썸네일은 별도의 API/QC 경로다. API 키를 설정했다고 본문 이미지 생성 경로가 자동으로 API로 바뀌지 않는다.

실제 저장 성공 2건은 각각 165.6초/179.5초이며 before-submit→after-submit이 87.1초/89.3초였다. 모델 생성 외 입력/제출 준비도 측정해야 한다. 두 표본만으로 평균 성능이나 전체 10개 완료 시간을 단정하지 않는다.

기본 batch 허용 예산은 `10분 잠금 + 3분 준비 + 장당 17분32초`다. 10장은 3시간8분20초다. 이는 정상 예상 시간이 아니라 부모 타이머가 허용하는 예산이며 후처리는 별도다. 새 자동 workflow의 무기한 대기와 결합하면 사용자는 매우 오래 기다릴 수 있다.

수정은 안정적인 imageSlotId, 프로필별 작업 대기열, 기존 원격 생성 결과 회수, worker 생존/재시작 복구 순으로 해야 한다. 전송이 불확실한 작업을 무조건 다시 생성하는 방식은 피한다.

## 6. 증상 4와 6: MCP 복구와 일괄 대상 선정을 고쳐야 한다

MCP outbox는 동일 결과만 다시 보내 중복 실행을 막는 장점이 있다. 그러나 409/413/401 영구 오류도 다음 poll에서 계속 보내므로 새 job claim이 0회로 남는 경로를 재현했다. 서버 결과 한도는 900 KiB, 로컬 outbox는 8 MiB로 다르다. 조회 pagination은 업로드 제한을 해결하지 못한다. 같은 요청의 JSON 키 순서 변경만으로 idempotency 충돌도 발생한다.

자동 발행의 단건·bulk poll은 deadline 없는 for-loop다. 로컬 running이 고착되면 heartbeat가 중앙 lease를 계속 연장하고, 새 작업은 busy로 거절된다. 메모리 job Map은 재시작 때 사라져 중앙 job 및 실제 외부 결과와 연결을 잃을 수 있다.

일괄 예약은 `src/app/api/brandlinks/bulk-schedule/route.ts:142-148`에서 scheduledPublishAt이 이미 있는 READY만 선택한다. startDate를 전달해도 예약일 없는 READY는 대상이 아니다. 실행 스크립트 `scripts/bulk-schedule-publish.ts:236-237`도 같은 필터를 사용한다. 실제 route fixture에서 `limit:10,startDate` 요청이 success=true/targetCount=0/spawn=0으로 끝났다. 날짜를 요청으로 지정했다면 먼저 대상 선정 후 그 날짜를 배정하는 일관된 계약이 필요하다.

자동 workflow에 사람에게 건별로 묻는 코드 루프는 없다. 반복 질문은 자동 보강 불가·오류 응답·수동 승인 nextAction을 받은 호출 에이전트의 판단과 연결될 수 있다. 이미 받은 10개 실행 요청의 범위(대상·개수·방식·날짜)를 batch에 저장하고 하위 작업까지 계승해야 한다. 승인 요청 문구의 반복만 지우고 품질/발행 실패를 남기는 것은 충분한 수정이 아니다.

부품 테스트 외에 **현재 저장 형식과 같은 freeform 여행 초안**을 복제한 fixture로 전체 경로를 검사해야 한다. Spec-first 초안만 정상인 테스트로는 이번 문제를 검증할 수 없다. 실제 외부 게시/이미지 품질의 최종 검증은 이번 코드 분석과 별도 단계다.
