# Material workflow harness 1.3.123

## Scope and preservation

This release implements the workflow gaps found in the product-link → planning → manuscript → original/reference photographs → final checks → material readiness → publication audit. PC and ChatGPT preparation use the existing durable material runner; publication remains a separate selected, revision-bound operation. No production image generation, manuscript repair or post/schedule submission was initiated to test these changes.

The older 1.3.123 preservation baseline had already diverged before this implementation: two manuscripts and several asset bindings had changed, while its 565 existing image bytes survived. That observation is retained and is not attributed to this source patch or silently rolled back. The implementation baseline at `2026-10-12T13:15Z` contains exact copies of 72 current manuscripts/manifests and hashes of 568 referenced image files. Subsequent preservation claims use this separate immutable baseline.

## Corrected behavior

- Manual and automatic approvals invoke the same saved-text recheck, current publication pixel preflight and approval gate. Only that approval gate binds readiness. Diagnostic photo audits cannot promote an old approval.
- A signed success receipt must bind the current manuscript, final image/reference bytes, selected gallery, relevant source metadata and current review policy before a shopping material is ready. Approval/progress timestamps and an otherwise identical recheck timestamp do not revoke readiness. Body, photograph, reference, source or policy changes do. Policy identity uses canonical shipped source bytes and actual rules/schema/budget, independent of installation path and compiler-generated function names. The request-result cache includes that same policy, so old success cannot be re-signed after a validator-only change.
- Multiple photographs from one proven completed request are individually checked against the current product/reference and complete final publication text. If several pass, stable SHA ordering selects one and records every candidate result without regeneration or output deletion. Different requests, uncertain completion, changed inputs, invalid reviewer responses and unfinished owners remain blocked. Zero valid candidates report actual fidelity failure rather than ambiguity.
- `post_prepare_material` requires PC 1.3.123 and dispatches the existing full `MATERIALS_PREPARE` operation. Context preparation and manuscript submission are explicitly intermediate steps. MCP responses distinguish delivery completion from durable PC completion, keep the original workflow ID, and expose pending, input, authentication, outcome-check and blocked states. Current product membership, readiness and errors must agree; historical ready execution alone is insufficient.
- ChatGPT context receives the exact inspected original as a native image block using existing authenticated asset delivery. The snapshot and image SHA are checked before and after upload. URL-only, corrupted, changed or oversized references remain `needs_reference`; local paths are removed. The first paginated result page also delivers native reference pixels. The PC admission lock rechecks an existing source request before dispatch, preserving idempotent reconnects.
- Failure observations contain phase, outer/causal codes, product/revision/source snapshot, affected sections, protected asset SHA values, attempt and outcome. Raw model messages, paths and URLs are excluded from writer references. Only matching current product/revision/context observations produce bounded static guidance; changed sources or rewritten drafts discard old guidance. Existing retry budgets and normal documents/images remain protected.
- The Naver reader collects actual body components without document-title/UI text. Disclosure is checked immediately after insertion and again before submission. Bounded diagnostic evidence distinguishes missing/duplicate disclosure, hidden content, wrong focus and body-reader disagreement. Actual logged-in Naver DOM and a real submitted post remain outside the offline proof.
