# 블로그 자동포스팅 최종 수정·보강 방향

작성일: 2026-09-07 · 대상: MCP Sites + 데스크탑 1.3.25 · 코드 기준: `10634b6` 및 기존 작업 트리 변경.

**최종 권고는 ‘같은 작업·초안·이미지·평가·발행 결과를 앱과 MCP가 끝까지 공유하도록 수정’하는 것이다.** 예약 입력, 이미지 저장 충돌 등 직접 결함을 고치면서 평가와 작업 상태의 공통 계약을 함께 정리해야 한다. 화면 문구만 바꾸거나 점수 기준을 낮추면 승인 실패와 반복 요청이 남는다.

이 문서는 두 검사 결과를 대조한 최종 수정 명세다. 새 화면 검사·실제 발행·생성·운영 코드 수정·배포는 수행하지 않았다. 화면 자료의 관찰과 코드 재현, 이번 추가 코드 대조, 아직 확인되지 않은 원인을 구분했다.

## 4. 공통 설계 원칙 — 유지할 것과 바꿀 것

현재 Sites 중앙 큐와 데스크탑 실행 구조는 유지하는 것이 권장안이다. 전체 재작성보다 두 저장소 사이에 식별자·상태·결과 계약을 맞추는 것이 변경 범위와 회귀 위험을 줄인다.

### 작업과 결과의 기준

제안하는 공통 식별 필드: `workflowId/batchId → itemId → draftId+revision → sectionId → imageSlotId`, 실행 시도는 별도 `attemptId`. 초안 평가에는 `snapshotId, textHash, imageRevision, evaluatorVersion`을 연결한다. 이는 구현 제안이며 현재 전부 존재하는 필드가 아니다.

데스크탑 DB는 로컬 실행 상태의 권위, 중앙 큐는 원격 전달/조회 상태의 권위로 유지한다. 같은 correlation ID로 연결하고 상태 전환 이벤트를 중앙에 전달한다. UI는 둘을 임의로 섞어 ‘완료’를 계산하지 않는다. 중앙 전달 실패가 로컬 발행 성공을 실패로 덮어쓰지 않게 한다.

```text
요청 접수 → 대상 확정 → 원고 준비 → 이미지 준비 → 현재 버전 검수
                                      ↑                  ↓
                                  부분 보강 ← 해결 가능한 실패
                                                         ↓
                                       품질 승인 → 외부 제출 → 결과 확인
                                                         ↓
                                              게시/예약 확인 완료

제출 전 해결 불가: 해당 항목 보류/실패
제출 후 확인 불가: 결과 불확실 → 실제 결과 대조 → 재실행 여부 결정
중앙 보고만 실패: 전달 복구, 외부 제출 반복 금지
```

하위 작업 SUCCEEDED는 전체 workflow 완료와 다르다. job의 terminal과 workflow의 완료 상태를 별도로 반환한다. 실제 외부 제출은 네트워크 장애 아래 완벽한 exactly-once를 단정할 수 없으므로, 결과 불확실성을 보존하고 중복 제출을 금지하는 방식으로 설계한다.

### 승인과 보강의 기준

품질 통과 여부와 사용자의 실행 지시는 별도다. 사용자가 이미 요청한 대상·개수·발행 방식·일정 범위 안에서는 하위 항목마다 재확인을 요구하지 않는다. 근거 부족을 사용자의 승인 클릭으로 해결하지 않는다. 범위가 달라지거나 추가 비용 승인이 필요한 예외만 모아서 확인한다.

## 5. 수정 작업 묶음

아래 P0는 ‘이 제품의 자동포스팅 정상화를 위한 릴리스 필수 조건’을 뜻한다. 화면 보고서의 P0와 코드 보고서의 P1을 기계적으로 합산한 심각도 숫자가 아니다.

### R01 — 공통 품질 판정과 실패 근거 연결 [P0]

- 내용 평가, 이미지 평가, 상품 첨부 준비, 실행 준비를 분리하고 전체 승인 결과는 이 결과들로 한 번 계산한다.
- 생성/수정/재검사/발행 직전 검사에 동일 snapshot과 정규화 함수를 사용한다. 출처 변경은 새 버전으로 기록한다.
- specValidation은 생성 참고 결과로 남기고 현재 승인 readiness로 재사용하지 않는다. 최신 판정이 없으면 ‘미검사/재검사 필요’를 반환한다.
- failure에는 `sectionId, criterion, evidenceRef/문장 위치, 개선 조건`을 제공한다. 대표 error 문자열 하나로 보강 prompt를 만들지 않는다.
- 화면은 원고 80점 옆에 글 보강 이유, 이미지 영역에 슬롯 부족 이유를 보여준다. 이미지 추가만으로 원고 점수/텍스트 실패를 임의 변경하지 않는다.

변경 중심: `brand-post-package.ts`, `brand-post-revalidation.ts`, `brand-post-quality-display.ts`, `brandlink-content-readiness.ts`, `draft` API, `page.tsx`, MCP draft 응답.

완료 기준: 쇼핑/여행을 번갈아 열어도 상품·revision·점수·사유 일치. 높은 점수+필수 요소 실패를 정확히 설명. 오래된 spec READY가 현재 FAIL을 가리지 않음. 이미지 부족만 고쳐도 이미 통과한 글을 다시 작성하지 않음.

### R02 — 의미 기반 이미지 배치·슬롯·제작 이력 [P0]

- 문단을 섞거나 부분 보강해도 유지되는 sectionId를 부여하고, 각 이미지 위치에 안정적인 imageSlotId를 둔다. 이미지 경로 배열의 index로 연결하지 않는다.
- raw/checkpoint/cache/apply까지 같은 slot ID를 전달한다. 같은 슬롯 재시도는 결과 재사용, 서로 다른 두 슬롯은 구별한다.
- 이미지 요구를 장소/상품 대상·용도·근거로 구조화한다. 근거가 확인된 원본 후보를 우선 매칭하고 부적합/불명확한 사진은 자동 채움으로 통과시키지 않는다.
- 제작 결과가 실제 provenance를 저장하게 한다: 원본, 원본 합성, 생성 배경, 설명 카드 등. AI 생성 여부와 실물·실제 장소 증거 여부는 다른 필드다.
- 표시는 전체 이미지 수, 슬롯 충족 수, 생성 진행 수를 분리한다. 총 개수 충족이 문단 적합성을 대신하지 않는다.

**정책 변경 권고:** 현재는 문단마다 생성 이미지가 필수일 수 있다. 이를 ‘확인된 원본도 해당 슬롯의 목적을 충족하면 인정’으로 바꾸는 안을 권장한다. 이는 장수 제한 우회가 아니라 승인 정책 변경이다. 기존의 최소/권장/생성 필수 조건을 policyVersion으로 명시하고 테스트를 함께 변경해야 한다. 생성만 허용하는 정책을 유지한다면 그 비용·대기·필수 장수를 요청 전에 정확히 알려야 한다.

변경 중심: `post-composition-contract.ts`, `brand-post-image-generation.ts`, `brand-post-image-repair.ts`, `chatgpt-generate-image-batch.ts`, package provenance, 이미지 미리보기.

완료 기준: 시티투어/모스크/호텔에 의미가 맞는 사진 유지. 문단 재정렬·부분 보강 뒤 연결 불변. 최소 2장 섹션에 다른 두 장 적용. 한 장 성공 뒤 중단하면 남은 슬롯만 복구. 원본 합성에 AI 실사 라벨이 붙지 않음.

### R03 — 저장 MCP 초안의 자동 보강 지원 [P0]

- postSpec 없는 freeform도 snapshot 근거로 부분 수정할 경로를 제공한다. 현재 저장 형식을 지원하는 방식이 우선이며, Spec-first 강제 변환은 본문/이미지 매핑 보존 검증 전에는 기본 복구로 쓰지 않는다.
- workflow가 시작 전에 repair capability를 확인한다. 지원되지 않는 형식으로 보강을 시작했다가 INVALID_INPUT으로 끝내지 않는다.
- 실패한 문단/슬롯만 보강하고 통과한 부분은 보존한다. 수정 전후 판정과 변경 범위를 기록한다.
- 전체 보강 횟수는 batch 정책에 고정한다. 초기 권장값은 최대 2회이며 개선 없으면 조기 중단한다. 이는 제안값이다. 내부 엔진/상위 workflow가 각각 횟수를 늘려 총 호출이 증폭되지 않게 한다.

변경 중심: `draft/route.ts`, `simple-agent.ts`의 revise 경로, `scheduled-draft-workflow.ts`.

완료 기준: 출처가 있는 기존 MCP 여행 초안이 저장→내용 보강→이미지 충족→같은 평가로 승인→발행 준비까지 이어짐. 출처 없는 초안은 사실을 만들지 않고 명확하게 보류. 실패가 새 원고 전체 재작성이나 사용자 승인 질문으로 반복되지 않음.

### R04 — 영속 작업·상품별 진행·재시작 복구 [P0]

- 메모리 Map/useState만으로 실행 상태를 관리하지 않는다. batch/item/attempt 상태, worker 소유자, heartbeat, 단계별 deadline, 마지막 확인 시각을 저장한다.
- 페이지 mount/탭 복귀 시 active workflow를 조회하고 같은 작업번호·선택 탭·상품별 진행을 복원한다. 버튼 활성화는 서버가 반환한 실행 가능 상태를 기준으로 한다.
- 로컬 큐는 대기/실행/부분 보류를 구분한다. 10개 중 한 개 준비 중이라면 전체가 ‘대기10’으로만 남지 않는다.
- 앱 시작 시 소유자 없는 running을 checkpoint와 대조한다. 발행 제출 이후는 임의 READY 복구 대신 결과 불확실로 남긴다.
- HTTP deadline, 작업 deadline, lease를 구분한다. heartbeat가 온다는 이유로 진척 없는 작업을 영원히 연장하지 않는다.

변경 중심: 로컬 DB job/event 모델, `desktop-activity.ts`, auto/bulk routes, `scheduled-draft-workflow.ts`, 이미지 worker, `RemoteAgentPoller.tsx`, Home 전역 진행 조회.

완료 기준: 페이지 이동·앱 재시작·MCP 재조회 뒤 같은 batchId와 10개 항목 복원. 두 번 클릭/재접속에도 외부 제출 중복 없음. 죽은 worker와 정상 장기 작업을 구분. 읽기 전용 작업은 무관한 실패 하나로 영구 차단되지 않음.

### R05 — 예약 입력·일괄 대상·실제 발행 결과 검증 [P0]

- 상품/주제글의 native prompt를 날짜·시간·시간대 입력으로 교체한다. 취소·잘못된 날짜·API 실패를 명시적으로 처리한다.
- `startDate`가 주어지면 먼저 READY 대상을 고정한 후 일정 배정. API와 bulk 스크립트의 not-null 필터를 함께 수정한다. 대상 0건은 ‘10건 완료’와 구별한다.
- 계획 시각, 준비 상태, Naver 제출 중, 예약 확인 완료를 별도로 저장한다. 예약 준비 중 예정 시각을 넘겼을 때 기본 권고는 보류다. 재배정은 이미 정한 정책이 있을 때만, 즉시발행으로 자동 전환하지 않는다.
- 최종 클릭 실패를 성공으로 반환하지 않는다. 글 URL parser를 공용화하고 호스트·계정·글 번호를 검증한다.
- Naver 응답의 업무 성공/등록 식별자 및 실제 글/예약 항목을 확인한다. HTTP 200이나 버튼 클릭만으로 완료 판정하지 않는다.
- 제출 후 연결 끊김, URL 지연, DB 기록/cleanup 실패는 제출 전 실패와 구분한다. 이미 확인된 성공을 cleanup 실패가 덮어쓰지 않는다.
- UTC 저장과 Asia/Seoul 표시를 명시하고 OS/서버 시간대에 기대지 않는다. 게시판 이름/번호도 같은 실제 설정에서 보여준다.

변경 중심: `page.tsx`, `publish`/`bulk-schedule`/`verify` routes, `simple-agent.ts`, `naver-schedule-submission.ts`, `kst.ts`, Sites 시간 표시.

완료 기준: 개별/일괄 일정 일치, 실제 예약 항목과 KST 시각·게시판 일치. 제출 전 오류만 일반 재시도 가능. 제출 뒤 응답 유실·STOP·정리 오류에서도 중복 글 생성 없이 결과 대조. 날짜 선택이 되는 것만으로 완료 판정하지 않음.

### R06 — MCP 결과 전달·도구 노출·전체 목표 추적 [P0]

- 현재 소스에 있는 job_result_read가 실제 배포 커넥터와 해당 세션의 tools/list에도 노출되는지 검증한다. ‘없다’는 대화 설명만으로 도구를 중복 구현하지 않는다.
- 첫 응답은 상품/초안 식별정보, 단계, 차단 사유, 다음 호출, 전체 workflow 상태를 항상 포함한다. 원고 작성에 필요한 출처는 보존하고 중복 prompt/snapshot 표현만 줄인다. 필요한 상세 근거는 권한 있는 페이지/섹션 조회로 읽게 한다.
- 중앙 완료 upload 한도와 outbox 한도를 통일한다. 큰 결과는 저장 완료 전에 chunk/object 참조 계약으로 전송한다. 조회 paging과 업로드 크기 문제를 별도로 해결한다.
- 일시 네트워크 오류는 동일 완료 body만 재전송한다. 401/409/413 영구 오류는 기록·대조·격리해 끝나지 않는 pending 루프를 끊는다. 성공한 발행 결과는 보존한다.
- idempotency 비교는 정규화된 의미와 canonical hash 기준으로 한다. 같은 인자 키 순서만 바뀐 재시도는 같은 job으로 연결한다.
- `job terminal`과 `workflow outcome`을 분리한다. 준비 완료가 발행 완료 안내를 유발하지 않게 한다. RUNNING에는 동일 작업 조회/링크를 제공한다.
- 대화 턴이 끝나도 worker는 계속 실행하고 최종 결과는 앱/사이트의 지속적인 작업 상세에서 조회 가능해야 한다. 최종 알림 기능을 추가한다면 사용하는 호스트/커넥터가 지원하는 방식으로 구현·검증한다. prompt의 ‘계속 조회’ 문장만으로 이를 보장하지 않는다.

변경 중심: `apps/sites` MCP/job/result API, tool schema, `remote-agent/poll`, `remote-agent-completion`, `draft-context-view`, 중앙/로컬 job correlation.

완료 기준: 94,472자급 결과를 실제 연결 세션에서 읽고 다음 단계 진행. 원고 원문 유실 없음. RUNNING 뒤 성공/실패에 지속 접근. 401/409/413·응답 유실에 외부 작업 재실행 없이 복구. 키 순서 변경은 conflict 아님.

### R07 — 이미지 오류별 복구와 batch 지속 정책 [P0]

| 오류 종류 | 권장 처리 | 다른 항목 처리 |
|---|---|---|
| 생성 거절 | 사유를 구분하고 확인된 원본/허용 가능한 대체 장면/보류로 수렴. 같은 요청 반복 금지 | 독립된 정상 상품 계속 |
| 전송 완료 여부 불확실 | request/conversation/artifact 참조로 기존 결과 확인. 새 생성부터 시작하지 않음 | 프로필 사용 가능 여부에 따라 대기 또는 계속 |
| 생성 완료·다운로드/적용 실패 | 다운로드/적용 단계만 재개, 성공 checkpoint 보존 | 정상 항목 계속 |
| 로그인/계정·공통 공급자 장애 | 계정 조치 필요로 구분, 영향받는 실행을 잠시 멈춤 | 같은 장애를 10번 반복하지 않음. 다른 공급자 작업은 정책에 따라 계속 |
| 원본 사진/상품 근거 없음 | 생성 전 검증해 낭비 차단, 자료 필요/보류로 반환 | 다른 상품 계속 |
| 임시 네트워크 실패 | 아직 제출하지 않은 단계/조회에 한해 제한 재시도 | 불확실한 제출 반복 금지 |
| journal 손상/worker 종료 | 검증된 완료 prefix 회수, 불확실한 마지막 슬롯 보존·복구 | 다른 완료 결과 무효화 금지 |

제안 오류 분류를 사용자 언어와 기계 판정 코드로 함께 제공한다. 일부 성공 API는 `completed/partial/blocked`와 잔여 슬롯/오류를 반환해야 하며, success=true만 보고 전체 이미지 완료로 처리하지 않는다.

완료 기준: 거절 상품 1개+정상9개 fixture에서 거절이 무한 재시도/재질문이 되지 않음. 부분 성공 유지. 성공 파일이 있는데 다운로드 실패 때문에 같은 이미지를 새로 생성하지 않음.

### R08 — 공통 작업함·히스토리·사용자 안내 [P0 핵심 / P2 화면 정리]

- 앱과 MCP 사이트에 같은 workflow/item/attempt로 접근하는 작업 상세를 제공한다. 상품명·현재 단계·마지막 변화·오류 원인·결과·재개 가능 동작을 표시한다.
- 현재 BrandLink 상태 목록과 실행 시도 이력은 분리한다. 이전 실패 후 재시도 성공도 과거 사건으로 남기며, 예약 성공과 준비 실패도 조회한다.
- 진행 배너는 전역 유지. 총점보다 ‘자동 처리 중/사용자 조치 필요’를 먼저 보여주고, 실패 문단·이미지를 바로 열 수 있게 한다.
- 최종 미리보기는 실제 사용하는 render plan에서 만든다. 원고·이미지·제휴 안내·상품 첨부를 합쳐 확인하고 Markdown 원문은 별도 탭으로 둔다.
- 중복 예약/즉시 버튼과 200개/50개/10개 도구가 섞인 실행 영역을 정리한다. 선택한 대상과 개수를 하나의 실행 영역에서 확인한다.
- 계정 연결, 원고 엔진, 본문 이미지 엔진, 썸네일 방식, Naver 게시 준비를 각각 표시한다. MCP OAuth 연결과 PC 페어링도 구분한다.
- 키워드 참고 QC의 이미지5/해시태그15와 여행 실제 승인 기준이 같은 검사처럼 보이지 않게 유형·policyVersion을 표시한다. 내부 API/contract/legacy 용어와 다른 모드 도움말을 정리한다.

완료 기준: 앱 이력0/사이트FAILED처럼 범위가 다른 화면은 원인과 연결 경로를 명시. 실패 상세에서 상품·원인·진행 기록 접근. 페이지를 이동해도 같은10건 진행. UTC/KST·게시판 값이 일치. 표지 제작법과 실제 적용본이 일치.

### R09 — 비용·시간·성공률 계측 [P1]

- 수집, 글 작성, 보강, 이미지 queue 대기, composer 준비, 입력, 전송, 생성, 다운로드, 합성/검수, 적용, 외부 발행, 결과 확인, MCP 전달 시간을 분리한다.
- 기존 성공 이미지 2건의 전체 165.6/179.5초, 입력·제출 함수 87~89초를 초기 단서로 삼되 평균/병목 원인을 단정하지 않는다. 화면의 1→6장 진행도 별도 관찰 시각의 값이다.
- 글당 생성필수 수, 원본 재사용 수, 실제 provider 호출 수, 재시도와 보강 횟수를 기록한다. 10개×10장=100장은 재시도·보강을 제외한 초기 작업량 예시다. 추가 슬롯·재시도로 초과할 수 있고 이미지 장수와 provider 호출 횟수는 다르므로 확정 비용으로 사용하지 않는다.
- 성능 목표는 원본 충분/생성 필요, 쇼핑/여행을 나눠 기준 표본에서 정한다. 단순히 timeout을 짧게 만들거나 이미지를 무작정 병렬 생성해서 지연을 숨기지 않는다.
- 성공률 분모는 발행 시도다. 목록조회/근거준비 성공을 발행 성공으로 합산하지 않는다. 사용자 지시가 허용한 비용·범위를 batch에 기록한다.

완료 기준: 느린 항목의 대기와 실제 생성 시간을 구분할 수 있음. 원본 재사용/불필요 재생성 감소를 수치로 확인. 10건 결과표의 성공·보류·실패·불확실 합이 선택한 대상 수와 일치.

## 8. 기존 자료 복구와 배포 조건

- 기존 manifest/원고/이미지/journal을 백업하고 읽기 자체가 migration을 수행하는 store 함수를 일반 진단용으로 쓰지 않는다.
- legacy 섹션 ID는 원래 본문과 연결을 보존하는 migration map으로 이전한다. 순번으로 새 ID를 덮어써 이미지 의미를 다시 바꾸지 않는다.
- 오래된 QC는 현재 기준으로 재검사하되 기존 발행 확인 결과는 보존한다. running은 worker/checkpoint 대조 후 복구하고 FAILED를 일괄 READY로 초기화하지 않는다.
- outbox 영구 오류는 원 결과를 격리·대조한다. 보관함 삭제나 새 idempotencyKey 발급만으로 정상화를 처리하지 않는다.
- 프로토콜 변경은 capability/version 협상으로 호환성을 확인한다. Sites 지원을 먼저 준비하고 호환 데스크탑을 배포한 뒤 새 기능을 활성화하는 방식을 권장한다.
- 이 프로젝트의 공개 MCP 사이트는 `apps/sites` Sites 경로다. Windows 설치본/업데이트 피드는 별도로 검증·게시해야 한다. 현재 `.openai/hosting.json`과 package script를 확인했으며 Vercel 배포로 대체하지 않는다.
- 배포 후 installed version/source와 중앙 capabilities, 저장 초안 재개, 실제 결과 조회를 확인한다. 소스 수정·빌드·배포·설치·실게시 성공을 각각 증거로 남긴다.

## 9. 피해야 할 임시 처방

1. 80/96점이므로 강제 승인: 필수 내용 실패와 이미지 부적합을 숨긴다.
2. 모든 본문 재작성: 출처/섹션/이미지 연결을 다시 깨뜨리고 비용을 늘린다.
3. 무조건 이미지 재생성 또는 timeout 확대: 슬롯 충돌과 이미 전송한 결과의 복구 누락을 해결하지 않는다.
4. 프런트엔드 busy만 해제: 서버 실행 상태와 무관한 중복 조작을 유도한다.
5. 모든 FAILED를 재시도: 실제 게시된 글을 다시 올릴 수 있다.
6. MCP prompt에 ‘계속해’만 추가: 도구 노출·큰 결과·영구 전송 오류·지속 작업 상세를 해결하지 않는다.
7. 소스에 reader가 있으므로 커넥터 정상이라고 판단: 실제 세션의 노출과 후속 호출까지 확인해야 한다.
8. UI에 보인 과거 불완전 상태를 현재도 고착 중으로 판단: 관찰 시각과 이후 진척을 구분해야 한다.

## 10. 이번 통합 리포트의 검증 범위

원본 화면 REPORT/HANDOFF/BROWSER-EVIDENCE/EVIDENCE-INDEX와 기존 코드 보고서들을 대조했다. 이번에는 F01/F02의 사유·집계 코드, freeform 이미지 순번 배치, 페이지 상태 복원, 앱/사이트 이력 조회 범위, MCP reader 노출 코드, 서버 시간 표시, Sites/업데이트 경로를 추가로 읽었다. 새 화면 캡처나 브라우저 조작은 하지 않았다.

추가로 실제 resolvePostDocument를 메모리 입력으로 호출해 순번 배치/문단 재정렬 문제를 확인했다. 운영 파일·브라우저 이미지를 입력하거나 변경하지 않았다. 최신 manifest의 이미지 완료/원고 미통과 상태는 JSON 읽기만으로 확인했다.

이전 코드 검사 증거는 기존 MCP 17/17 PASS, 새 MCP 결함 재현 5/5 PASS, 승인/발행/이미지 재현 PASS, 이미지 batch 23개 및 timeout 검사 PASS, TypeScript 진단 없음이다. 초안 표시 순수 테스트 1개는 버튼 문구 정규식 불일치로 실패했다. 이번에는 운영 코드를 바꾸지 않았으므로 같은 테스트를 반복한 것을 새 수정 검증으로 보고하지 않는다.

최종 문서 대조 검토에서 사례 혼합/과장에 대한 차단 사항은 없었다. 이미지 초기 작업량과 provider 호출 수를 구분하고, category/code-only 내용 실패를 승인 회귀 항목에 추가했다. 문서 내 상대 링크 11개가 모두 존재하는 것도 확인했다.

쇼핑 실초안, 과거 MCP 실패의 정확한 errorCode, 실제 세션 reader 노출, Naver 게시/예약 결과, 계정 제한과 지연의 인과관계는 아직 확정되지 않았다. 이들은 최종 검증 항목으로 남겼다. 이 문서는 **수정 방향 정리 완료**이며 **기능 수정/배포/운영 정상화 완료** 보고가 아니다.
