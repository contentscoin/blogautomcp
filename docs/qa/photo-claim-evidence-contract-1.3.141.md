# Windows 1.3.141: 사진 주장 검수의 원문 근거 계약

이 변경은 사진에 관한 부정 판정이 실제 원고의 어느 표현을 근거로 했는지 추적합니다. 설치된 1.3.140의 실제 검수에서 취향을 조건으로 한 선물 조언을 사진 속 여러 종류의 구성 단정으로 읽은 사례와, 일반 중량 안내를 사진이 전체 구매 수량을 입증한다는 주장으로 읽은 사례를 확인했습니다. 이 두 판정은 입력 해석 오류가 의심되지만, 부정 판정을 임의 승인으로 바꾸거나 정상 원고를 반복 삭제하는 방식으로 처리하지 않습니다.

문서 작성 시 설치 버전은 1.3.140이며 현재 준비완료로 보고된 소재는 3개입니다. 1.3.141의 빌드·업데이트 배포·설치·실제 MCP 최종 승인은 아직 진행하지 않았습니다. 새 정책에서는 이전 승인도 새 최종검수를 통과해야 합니다.

## 원문과 연결하는 검수 응답

최종 이미지 검수 요청은 실제 발행 소제목과 본문 문단을 `claimSources`로 제공하며, 본문에 0부터 시작하는 문단 번호를 부여합니다. 응답의 `photoClaimObjection`은 다음 5개 필드를 필수로 반환합니다.

| 필드 | 의미 |
| --- | --- |
| `origin` | `none`, `section-title`, `section-body`, `thumbnail-headline` 중 근거 위치 |
| `sourceIndex` | 본문 문단의 0 기반 정수 번호. 소제목·썸네일·근거 없음은 `null` |
| `quote` | 실제 소제목 전체 또는 해당 본문 문단 전체의 정확한 원문 |
| `scope` | 외형·수량·전체 구성·성능·결과 중 사진 주장 범위, 또는 `none` |
| `conflict` | 해당 주장과 실제 픽셀의 구체적인 충돌 설명 |

`photoClaimMatches=true`이면 근거 객체는 정확히 `origin=none`, `sourceIndex=null`, 빈 `quote`, `scope=none`, 빈 `conflict`여야 합니다. `false`이면 유효한 위치와 비어 있지 않은 충돌 설명이 필요합니다. 본문·소제목 인용은 전체 문자열이 같아야 하며, 공백 제거·유니코드 정규화·부분 인용·수치 변경으로 일치를 만들어내지 않습니다. 이 검증은 응답을 수정하거나 불리한 boolean을 유리하게 바꾸지 않습니다.

검수 지시는 취향 조건, 사용·보관 조언, 구매 옵션 확인과 일반 상품 규격이 그 자체로 사진의 구성·수량·성능을 입증한다는 주장이 아님을 구분합니다. 반대로 실제 사진의 외형·개수·전체 구매 구성·성능 증명에 관한 단정은 픽셀과 근거에 맞아야 합니다. 정확히 인용된 부정 판정도 자동으로 뒤집지 않습니다.

## 실패 처리와 유지한 차단 기준

근거의 위치·문자열·구조가 맞지 않으면 `INVALID_REVIEW`로 실패를 유지합니다. 진단에는 잘못된 근거와 원래 판정·이유를 보존하되 표시 과정에서 로컬 경로와 자격 증명을 가립니다. 잘못된 인용을 이미지 자체의 의미상 불량으로 확정하거나 자동 원고 수정 대상으로 만들지 않습니다. 해당 노드의 기존 거절 기록도 지우지 않습니다.

다른 상품·옵션, 정체성 미확인, 공지 이미지, 추가 설명 문구·프레임·콜라주, 실제 수량·구성·성능 오인과 불가능한 배치는 계속 차단합니다. 근거가 잘못된 응답에 독립적인 상품·형식 오류도 있으면 기존 `SEMANTIC_REJECTION`도 유지합니다. 사진 주장 검사가 정상이어도 최종 `accepted=false`인 기존 부정 판정은 그대로 거절합니다. 원래 boolean 파서와 최종 불리한 판정 조건은 변경하지 않았습니다.

새 의미 검수 재호출, 이미지 재생성, 원고 자동 교정은 추가하지 않았습니다. 기존 provider 재시도와 형식이 깨진 JSON 응답에 대한 기존 제한적 재시도는 그대로입니다. 검수 입력이 같은데 유리한 답을 얻기 위해 반복하는 경로는 추가하지 않았습니다.

## 확인한 결과

| 검증 | 결과와 범위 |
| --- | --- |
| 오프라인 최종 감사 | 232개 시나리오 통과. 전체 원문·번호·공백·수치·유니코드 불일치, 잘못된 객체, 부정 판정 보존, 재호출 차단 포함 |
| 참조·저장·호환 회귀 | 참조 107개 시나리오 및 기존 영수증·거절 기록·사진 설명 복구·배칭·판매자 후보·참조 장면 회귀 통과 |
| 통합 검사 | 전체 TypeScript, 소재 회귀 29개 suite, 소유 파일 lint 통과 |
| 독립 소스 검토 | 21개 반례 검토 통과. 기존 파서·불리한 조건·정책 파일 목록 보존 확인 |
| 실제 Codex 사전 검수 | 두 소재의 기존 최종 사진 각 5개 모두 통과. 비교 자료 분할을 포함한 양성 요청 14회로 실제 최종 사진 10개를 검수 |
| 실제 음성 사례 | 최종 첨부 하나를 명백히 다른 상품으로 바꾸면 `identityMatches=false`, `accepted=false`. 실제 트레이 4개 사진에 거짓 트레이 12개 단정을 넣은 격리 요청은 정확한 전체 원문 근거와 함께 `photoClaimMatches=false`, `accepted=false` |
| 실제 사전 검수 보존 | 고유 `runCodexDraft` 요청 16회, 사용자 파일 640개·소스 17개 전후 바이트 동일. 원고·사진 수정, 이미지 생성, 소재 승인·블로그 발행 없음 |

실제 사전 검수는 기존 production 감사와 모델 경로를 사용한 한 차례의 제한된 실행입니다. 양성 요청 14회와 음성 2회는 서로 다른 입력이며 같은 요청을 다시 보내 통과를 유도하지 않았습니다. SDK 내부 네트워크 시도 횟수는 별도로 계측하지 않았습니다. 두 음성 입력은 임시 요청에만 적용했으며 실제 소재의 이미지 배정이나 원고에 저장하지 않았습니다. 사전 검수 경로는 성공 영수증·거절 기록·승인 상태를 쓰지 않았습니다.

정책 파일 목록은 기존 15개 그대로입니다. 설치된 1.3.140 대비 감사 파일 1개의 바이트가 변경되고 나머지 14개는 같습니다. 구조화 근거 필드와 검수 설명이 정책 지문을 변경하므로 이전 HMAC 영수증·승인을 새 정책의 성공으로 재사용할 수 없습니다. 배포·설치 후 실제 네이티브 경로에서 새 최종검수와 승인이 필요합니다.

## 한계와 남은 완료 조건

정확한 인용은 추적 가능성을 보장하며 문장 의미의 정확성을 보장하지는 않습니다. 모델이 실제 조건문 전체를 정확히 인용하면서 의미를 잘못 해석하면 이 검증만으로 오류를 교정할 수 없습니다. 썸네일은 정본 OCR 문자열이 없어 `thumbnail-headline`의 역할·형식만 검증하며, 인용과 실제 제목 픽셀의 일치를 기계적으로 보증하지 않습니다. 별도의 실제 픽셀 검수와 기존 부정 판정 차단은 계속 필요합니다.

독립 채택 검토 이후 빌드·패키징·정상 업데이트 설치와 실제 MCP 최종검수·승인 결과를 확인해야 합니다. 기존 원고·정상 사진·과거 실패 증거는 보존합니다. Offon의 과거 발행 확인 보류와 중복 발행 가드는 유지하며, 이 변경으로 블로그 발행이나 예약은 실행하지 않습니다.
